# Build contract — Premium & Payment

Source of truth: `docs/premium-payment-plan.md`, plus `docs/employer-billing-plan.md` (Employer details),
`docs/specs/{candidate,employer,admin,system-shared,ml-matchscore}.md`.
This contract resolves the plan's open questions (plan §15) and fixes conventions. **Where the contract and the plan
disagree, the contract wins.** If you find a real conflict or gap, make the smallest sensible decision, implement it,
and record it in your report under `decisions` — do not stop to ask.

## 1. Process rules (every agent)

For MySQL verification create a scratch database `hotjob_verify_<phase>` (`mariadb -uroot -e "CREATE DATABASE ..."`), point the app at it with env var `ConnectionStrings__DefaultConnection="Server=localhost;Database=hotjob_verify_<phase>;User=root;Password=;"`, and drop it afterwards. `dotnet ef migrations add` does not connect (DesignTimeDbContextFactory hard-codes `hotjob`, harmless). Never run `dotnet ef database update` without `--connection` pointing at a scratch DB.

- Code/identifiers/UI copy/error messages are English (the existing UI is English even though the docs are Vietnamese).
- Match the surrounding code: file-scoped namespaces, primary-constructor services, `ServiceResult<T>` + `ServiceErrorType`, XML `<summary>` on public types/members, `// ponytail:` comments for non-obvious decisions (existing convention). No TODO stubs, no half-wired features, no silent `catch`.
- Append your phase's result to `.superpowers/sdd/premium-payment/progress.md` (only the Gate agent writes the final ledger entry; implementers put names/decisions in their report).

## 2. Architecture conventions

- Models: `hotjob/Models/Billing/` (`hotjob.Models.Billing`): `Plan`, `Payment`, enums `PlanAudience {Employer, Candidate}`, `PaymentPurpose {EmployerPlan, EmployerFeatured, CandidatePremium}`, `PaymentStatus {Pending, Paid, Failed, Expired}`. Enums use the default int storage like existing enums. Money is `decimal(18,0)` VND.
- Services: `hotjob/Services/Billing/` (`hotjob.Services.Billing`) with the interfaces named in plan §4: `IEntitlementService`, `ICandidatePremiumService`, `IVnPayService`, `IBillingService`, `IBillingAdminService`; options classes `VnPayOptions` (section `VnPay`) and `BillingOptions` (section `Billing`). Register everything in `Program.cs`.
- Blazor pages call services directly through DI (no HTTP loopback — see `docs/superpowers/plans/2026-10-12-remove-api-loopback-clients.md`). The only new public HTTP endpoints are `VnPayController`: `GET api/vnpay/ipn` (server-to-server, replies JSON `{"RspCode","Message"}`) and `GET api/vnpay/return` (browser return: verify + process idempotently, then 302 to a result page). Other API controllers are optional.
- Use the already-registered `TimeProvider` for "now" in all new services (tests inject a fake). Never `DateTime.UtcNow` in new business logic.
- Pages: `@rendermode InteractiveServer`, `<AuthorizeView Roles="...">`, user id from `AuthenticationStateProvider` (`ClaimTypes.NameIdentifier`), and handle the "AuthSession not yet restored after a reload / return from VNPay" race exactly like `Components/Pages/Employer/Jobs.razor` (subscribe to `AuthenticationStateChanged`, load when authenticated). Sequential awaits only — never `Task.WhenAll` over calls sharing the scoped `DbContext`. Styling: reuse `wwwroot/css/Workspace.css` classes (`workspace-*`); a page-specific stylesheet goes in `wwwroot/css/` and is linked in `Components/App.razor` like the others. Every page shows loading, empty and error states.
- Tests: one file per area under `Tests/hotjob.Tests/<Area>Tests/`; reuse `TestFixture`; add helpers under `Support/`. Every business rule of the phase that appears in plan §12 / employer-billing-plan §10 gets a test that asserts real behaviour (no tautologies, no assertion-free tests). Time-dependent behaviour is tested with a fake `TimeProvider` (a tiny hand-written one in `Support/` is fine, or the `Microsoft.Extensions.TimeProvider.Testing` package).
- Migrations: after model changes run `dotnet ef migrations add <Name> --project hotjob/hotjob.csproj` from the repo root, read the generated file (it must contain only intended changes and be valid for MySQL/Pomelo), and verify it on a scratch DB. One migration per phase, descriptive names.
- Seeding: `DatabaseSeeder` seeds plans idempotently **by Code** (insert missing codes only; never overwrite admin-edited values).
- EF queries must translate on **both** SQLite (tests) and MySQL/Pomelo (production). Avoid provider-specific behaviour (DateTimeOffset ordering/aggregates on SQLite, decimal `Sum` on SQLite, case-sensitivity, `GroupBy` over computed keys that only one provider can translate). If something cannot be translated on both, materialise a narrow projection first and finish in memory.

## 3. Decisions (resolve plan §15 and ambiguities)

- **D1 Scope:** build GĐ1–GĐ8 completely. Order: 1, 2, 3, 4, 5, 8, 6, 7.
- **D2 Premium offer:** no CV builder (it is not in any phase; the monetization advice says not to sell it). Premium sells: advanced match score with improvement hints, matching job alerts, Premium badge, profile boost in employer candidate search. `Premium.razor` copy is rewritten at GĐ5 to promise exactly what exists (remove the "AI CV score"/"Automatic CV builder" claims).
- **D3 Catalogue:** FREE 0đ/1 job/perpetual (DurationDays 0); STARTER 500.000đ/5 jobs/30 d; GROWTH 1.500.000đ/20 jobs/30 d; PREMIUM_MONTHLY 99.000đ/30 d (Audience Candidate, JobQuota 0). Featured job 200.000đ/7 d from `Billing:FeaturedPrice`/`Billing:FeaturedDays`.
- **D4 Callbacks:** IPN and ReturnUrl both go through the same idempotent `IBillingService.ProcessVnPayCallbackAsync`. The return endpoint is not auth-gated (the browser arrives on a fresh circuit); that is safe because signature + amount + Payment lookup gate it and the grant is bound to the Payment's own company/candidate. Result pages must show only non-sensitive facts (status, amount, purpose, txn ref).
- **D5 Idempotency:** claim `Pending → Paid` atomically (conditional `UPDATE ... WHERE Status = Pending` via `ExecuteUpdateAsync` or a concurrency token) in the same transaction as the entitlement grant; a second/concurrent delivery gets "already confirmed" (IPN RspCode 02) and grants nothing. Unique index on `VnpTxnRef`. Grant only if `vnp_ResponseCode == "00"` and `vnp_TransactionStatus == "00"`; amount compared as `long` (VND × 100) against the stored amount; unknown/forged → 97/01/04 per employer-billing-plan §6.3 and **no state change** before the signature check passes. Failed payment → `Failed` (never downgrades a `Paid`). Stale `Pending` (> 15 min after creation) is marked `Expired` lazily when encountered; no background job.
- **D6 Purchase semantics:** buying a *different* employer plan replaces the current one immediately (`PlanId`, `PlanStartedAt = now`, `PlanExpiresAt = now + DurationDays`); buying the *same* plan while it is active renews: `PlanExpiresAt = max(now, current expiry) + DurationDays`. Featured: `FeaturedUntil = max(now, FeaturedUntil) + FeaturedDays`. Premium: `PremiumUntil = max(now, PremiumUntil) + DurationDays`, `PremiumStartedAt` set when it was not active, `BoostUntil = PremiumUntil` on every grant. FREE is never purchasable.
- **D7 Quota:** effective plan = FREE when `PlanId` is null **or** `PlanExpiresAt < now`. Active jobs = company's jobs with `Status` Draft or Published (status-based; Closed/Expired are free). Enforced at `JobService.CreateAsync` **and** at `UpdateAsync` whenever a job moves from Closed/Expired into Draft/Published (re-opening must not bypass the quota). Over-quota legacy companies are grandfathered: nothing is deleted, only *new or re-opened* jobs are blocked. Error text: "You have used all {used}/{quota} job slots on your plan. Upgrade to post more." (map to a distinct, UI-detectable error so the page can show an Upgrade link).
- **D8 Roles & manual assignment:** only the company Owner (`Employer.IsOwner`, Active membership, Approved company) may buy plans/featured; other members are read-only. Admin may assign a plan manually; this writes an audit `Payment` row with `Amount = 0`, `Status = Paid`, `VnpTxnRef = "MANUAL-" + guid`, `Note` naming the admin — so it never counts as revenue.
- **D9 MatchScore (GĐ4):** features exactly as plan §4.1. Safe-division rules: job with no skills → no score is available (UI hides the badge with an explanatory line); job whose weights sum to 0 → use the count ratio for `MatchedWeightRatio`. `ExperienceGap = Σ ResumeSkill.YearsOfExperience − JobPosting.ExperienceRequired` (plan-literal). Rule score = `MatchedWeightRatio × 100` (clamped 0–100), `AlgorithmUsed = "weighted-rule"`. Training set = applications with status Offered (label 1) or Rejected/Withdrawn (label 0), **excluding applications auto-rejected by job closure** (their latest status-history note is "Job closed" — that is not a hiring decision). Train only when finished-application count ≥ `MatchScore:MinTrainingRecords` (default 50) **and** each class has ≥ 5 rows; otherwise report "insufficient data" and keep weighted-rule. Trainer: ML.NET `FastTree` binary classification (needs packages `Microsoft.ML` **and** `Microsoft.ML.FastTree`), fixed-seed 80/20 split, `AccuracyScore` from the hold-out. Model file `App_Data/models/matchscore.zip` (config `MatchScore:ModelPath`, relative to content root; add `App_Data/` to `.gitignore`); load lazily, thread-safe; a missing/corrupt file falls back to weighted-rule without throwing. A new model is promoted only if its accuracy ≥ the active model's; otherwise the old model stays and the run is still logged (`ModelTrainingLog` gets an `IsActive`/promoted flag). `MatchScore` rows are upserted by (JobPostingId, ResumeId) with `AlgorithmUsed = "FastTreeBinary"` for model scores and recomputed when stale (skills changed on either side, or the model was retrained after `CalculatedAt`). Basic % is visible to every candidate; the advanced breakdown (matched/missing skills by weight, experience gap, improvement hints) is Premium-only and **enforced server-side** (GĐ5).
- **D10 Premium gate:** `ICandidatePremiumService.IsPremiumAsync` ⇔ `PremiumUntil > now`; expiry is automatic (checked on use).
- **D11 Job alerts (GĐ6):** when a job becomes Published (created Published, Draft→Published, re-opened), notify each Premium candidate whose best resume scores ≥ `JobAlerts:MinMatchPercent` (default 60), once per (candidate, job) — add `Kind` and `RelatedJobPostingId` to `Notification` for dedupe/filtering. In-app only. Page `/job-alerts` (Premium) + nav link; free candidates get none and see an upsell.
- **D12 Candidate search (GĐ7):** `Candidate.IsDiscoverable` (default false) toggled on the Profile page; Employer page `/employer/candidates` (Active member of an Approved company) filters by skills / min years; ordering `BoostUntil > now` first, then newest; label "Featured"; Premium badge; exposes only name, position, summary, skills+years — never email/phone/DOB/address.
- **D13 Demo data:** `DemoSeeder` additions only when demo seeding is configured: demo candidate gets 2 resumes with different skill sets, demo employer is on FREE with exactly 1 published job; optional `Seed:Demo:SyntheticApplications` (default 0) creates finished applications so the ML demo can train.
- **D14 VNPay:** `vnp_Version=2.1.0`, `vnp_Command=pay`, params per employer-billing-plan §6.2; HMAC-SHA512 over the ascending-sorted `key=urlencode(value)&…` string excluding `vnp_SecureHash`/`vnp_SecureHashType` and empty values; `vnp_CreateDate` in GMT+7 (`yyyyMMddHHmmss`), `vnp_ExpireDate` +15 min; `vnp_TxnRef` unique ≤ 34 chars; `vnp_OrderInfo` ASCII without diacritics; client IP from the request (fallback `127.0.0.1`); signature compared with `CryptographicOperations.FixedTimeEquals`; amount never accepted from the client.
- **D15 Config:** keys per plan §7.4 (`VnPay:TmnCode/HashSecret/BaseUrl/ReturnUrl/IpnUrl/Version/Locale`, `Billing:FeaturedPrice/FeaturedDays`). `appsettings.json` carries non-secret defaults with **empty** `TmnCode`/`HashSecret`; the app must boot without them, and checkout then fails with a friendly "Online payment is not configured." `.env.example` documents `VnPay__TmnCode`, `VnPay__HashSecret`, `VnPay__ReturnUrl`, `VnPay__IpnUrl`.
- **D16 Months for revenue:** revenue months are bucketed by Vietnam time (UTC+7) of `PaidAt`; stored timestamps stay UTC.

## 4. Quality bar

Money and entitlement code is adversarially reviewed: assume forged callbacks, replays, double delivery, concurrent delivery, cross-tenant ids, expired plans, and clock edges. Prefer fewer, deeper modules over many shallow ones. Every user-visible claim on a page must be backed by working behaviour.
